# TianjiTown 人工测试操作手册（新手版）

适用版本：`1.0.0-SNAPSHOT`。本手册保留原来的 12 组、50 个步骤及编号，按顺序执行即可。测试人员不需要阅读代码；每步都说明由谁操作、怎样操作、如何判断结果。

2026-09-13 文档对齐：资金速查、NEW-P0-05 购买及 NEW-P0-11 清算短款预期已按当前代码更新。已有“已执行”勾选保留为原执行记录，不表示更新后的预期已经复测；这些项目须重新核对本轮证据。

建议由两位测试人员承担主测管理员、协测管理员工作，并兼任下面的玩家身份；不再另设两个专用管理员账号。涉及配置、查钱和备份时会明确写“管理员”。没有准备好的项目记为“受阻”，不要靠猜测继续。

## 一、先认识本文中的人和物

### 测试人员与账号安排

采用 **9 个独立游戏账号，其中 2 个兼任管理员**，比原安排少 2 个专用管理员账号；不要求 9 位真人。测试人员可轮流控制不同账号，但需要同时在线、同时提交或保留旧页面的账号须各自保持独立客户端会话，不能用退出账号再登录另一个的方式替代。两人同时提交的步骤仍由两位真人分别操作。

下文直接按身份称呼玩家，不使用人物字母代号。建镇前的“甲镇镇长”等称呼指预定担任该身份的账号，此时仍没有正式镇籍；建镇后按实际身份操作。先填写实际游戏名；命令中的 `<甲镇副镇长的游戏名>` 等内容要整体替换为真实名字，包括去掉尖括号。身份变化后仍使用原账号，不能临时换一个账号顶替。

### 管理员兼任玩家的规则

“主测管理员”和“乙镇辅助成员”是同一账号；“协测管理员”和“无镇籍对照玩家”是同一账号。其余账号也可以由这两位测试人员控制，但不同玩家身份仍保留不同游戏账号，避免成员关系、等待时间和交易记录混在一起。

除下面三类测试外，管理员账号可以保持管理员身份，直接完成建镇、成员、访客、公共资金、Buff、投票、重启和删除等玩家流程，不需要在每一步反复撤销、恢复权限：

1. **命令权限测试：** 验证普通玩家不能执行管理命令时，执行该命令的账号必须临时撤销 TianjiTown 管理权限和 OP，并确认没有从权限组继承相同权限。测试完成后可恢复管理员权限。
2. **税收测试：** 验证 QuickShop、Jobs、GlobalMarketPlus 的收入税和无镇籍免税时，实际收款账号必须以普通玩家权限完成交易。用于查账、改配置的管理员账号可以保持管理员身份。
3. **实际领地拦截：** 验证外人不能放置、破坏、开箱或圈地时，执行被拦截动作的账号必须关闭 Residence 的保护绕过权限。该账号可以保留 TianjiTown 管理权限，因为此处检查的是 Residence 是否真正拦住动作。

需要两种身份同时在场时仍使用两个不同游戏账号。例如双人同时审核必须使用两个账号，不能用同一账号的两个窗口替代。旧页面测试也必须保留原玩家账号和原页面，但该账号是否具有管理员身份只按上面三类例外处理。

### 开关和额外检查

本手册主流程按公共消费、Buff 商店、税收都开启执行。需要上线的功能如果关闭，须记录关闭范围，不能把没有执行的步骤写成通过。

管理员还需完成同一份源码的自动测试：在项目根目录执行 `mvn -B test`，保存完整结果，确认各模块没有失败或错误；仅看到测试文件存在不算通过。

建筑方块返还、领地信标、HuskSync、PlugMan、市场采购／拍卖、异常断电等需要额外的专项检查。本手册通过不等于这些功能也通过。原清单引用的 `P0_COMPRESSION_REVIEW.md`（自动检查映射 E01～E19）和 `P0_SPECIAL_TESTS.md`（专项要求）在当前工作区缺失，负责人需补齐材料并核实本轮适用的成功报告；首次测试或缺少适用记录时，不能直接判定可验收。返还和信标默认开启，如缺少专项成功记录，必须在拟上线服务器的实际配置中关闭并记录差异。不要为了方便仅关闭测试服上的功能。

## 三、每一步怎样记录和判断

### 完成标记

每个编号步骤都有完成框和反馈栏。原有勾选保留；勾选表示“做过”，不自动表示“通过”。开始新一轮时请复制一份清单并重置该副本的完成框。

| 结果            | 何时填写                                                   |
| --------------- | ---------------------------------------------------------- |
| PASS（通过）    | 该步骤的所有操作已执行，实际结果全部符合要求，有截图或记录 |
| FAIL（失败）    | 操作可以执行，但至少一项实际结果不符合要求                 |
| BLOCKED（受阻） | 缺账号、权限、场地、查询方式等，无法完成判断；写明缺什么   |
| NOT_RUN（未测） | 尚未开始                                                   |

通过或失败都可勾 `[x]`；受阻或未测保留 `[ ]`。多项检查只做了一部分，不能把整步记成通过。

### 查结果的固定方法

玩家操作都从服务台或手册进入，不能用管理员命令替代玩家流程。下面的查询和辅助命令由乙镇辅助成员（兼任管理员）执行；都已写出完整前缀。游戏聊天中保留 `/`，服务器控制台中去掉最前面的 `/`。

| 要查看什么                         | 操作                                                                                                                              |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 启动是否完成                       | `/tianjitown status`；`READY` 表示初始化完成，`LOCKED` 表示被锁住，需要处理错误                                             |
| 甲／乙镇余额和资金锁定原因         | `/tianjitown money view pzeroa`、`/tianjitown money view pzerob`                                                              |
| 小镇状态、镇长、记录版本、领地名称 | `/tianjitown town view pzeroa`；乙镇把代码改为 `pzerob`。`ACTIVE` 表示正常使用中                                            |
| 玩家身份和访客名单                 | 玩家打开手册，在小镇资料、成员管理、访客相关页面查看并截图                                                                        |
| 甲镇收支                           | `/tianjitown ledger view pzeroa`，或成员从公共资产进入账本翻页；乙镇同理                                                        |
| 最近管理操作                       | `/tianjitown audit 20`                                                                                                          |
| 甲镇现有能力加成和到期时间         | `/tianjitown buff list pzeroa`；同时让玩家观察实际生命上限等属性                                                                |
| 数据记录与实际保护是否一致         | `/tianjitown land reconcile all`，不要加 `repair`；这次要先看差异，不能先修好再当作通过                                       |
| 生成综合检查报告                   | `/tianjitown diagnose 7`；等待完成后查看 `plugins/TianjiTown/diagnostics` 新生成的文件。`INCOMPLETE` 表示没查完，不表示通过 |

测试期间暂停无关的买卖、转账和职业活动，避免其他交易影响比较。每次会改钱、身份或地块的操作，先记录操作前状态，再记录操作后状态。记录涉及玩家的余额、甲镇余额、乙镇余额、清算余额，以及物品／角色／保护／Buff 的变化。管理员补钱、设置副镇长、创建商店也要记录，避免把准备时的变化误认为测试造成的变化。

税收界面会把同一天的多次收入合并显示，不能用“只有一行”证明只收了一次。管理员应提供逐笔账目和第三方交易历史，按时间、金额、玩家和业务号对应核对。若没有现成导出方法，管理员可在正常停服备份后，用 SQLite 查看工具打开数据库**副本**，在 `ledger_entries` 中查看 `business_key`（业务号）、`entry_type`（收支类型）、`amount_minor`（金额）、`balance_after_minor`（操作后余额）；商店税记录在 `quickshop_tax_records`，Jobs／市场税记录在 `external_income_tax_records`。金额字段按最小货币单位保存，例如精度为两位小数时 `10000` 表示 `100.00`。不要编辑这些表；实际逐笔结果应附在报告中。

### 钱应该怎样变化

先根据实际配置计算预期，再与页面报价和余额变化比较。下面的数字只是默认配置示例；配置不同必须重算。

| 操作                                       | 应该看到的变化                                                                                 |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 建镇，费用 5000                            | 申请人少 5000；新镇有 5000；清算账户多 5000；两名初始成员的钱不变                              |
| 捐款 100                                   | 捐款人少 100；目标镇多 100；清算账户多 100；另一个镇不变                                       |
| 管理员给甲镇调账 +100／-100                | 甲镇和清算账户都增加／减少 100；普通玩家和乙镇不变                                             |

激活地块每次比基础价格贵 5% 的相应次数，中心免费格不计次数。默认前四次分别为 `5000.00`、`5250.00`、`5512.50`、`5788.13`。首次一起买两格应付 `10250.00`。管理员计算非默认价格时，用“基础价 × 1.05 的（第几次付费 - 1）次方”，每格各自向上补齐货币小数位后相加。例如保留两位小数时，5788.125 收 5788.13，不是 5788.12；不要拿上一格已补齐的价格继续乘。

生命 II 级、两周的价格是“生命 I 级一周基础价 × 2 周 × 95% × 2 级”，默认 `38304.00`。I 级一周默认 `10080.00`。其他周数用 1 周 100%、2 周 95%、3 周 90%、4 周 85% 的折扣，最后按实际货币精度向上补齐。默认生命每级多 2 颗心，II 级多 4 颗心；按同一玩家购买前后的上限比较。

收入税按**收钱的人属于哪个镇**计算。税前收入 100、税率 10% 时，玩家到手 90，税为 10；补贴够时服务器再补 10，因此该镇和清算账户各增加 20。补贴不够时，在“本次税额、该镇本周剩余额度、该镇本 12 小时剩余额度”中取最小值作为补贴。例：税 10、两个剩余额度为 6 和 20，则补贴 6，小镇和清算各增加 16。测试尽量用能算出整数税额的交易；其他插件自己的手续费先关闭，或单独记录。

### 等多久、怎样测旧按钮和同时操作

- 普通操作最多观察 60 秒，启动最多等 180 秒；明确需要后台处理的步骤等“本轮处理间隔 + 30 秒”。Jobs 等待交接单中的实际发薪时间。超时先保存提示、查钱和业务号，再记受阻或失败，不要连续点击付款。
- “同时操作”需要两个真人客户端先各自打开待提交页面，约定倒数后同时确认，录下两边画面。管理员还应保存能够说明两个请求处理时间确实重叠的日志或记录。只看到聊天时间相近、或两人依次点完，不能证明同时处理；需重新安排该项，无法确认就记受阻。
- 身份变化、关开关时，一人保持旧页面不关闭，由管理员或另一人完成变化，再提交旧页面。有聊天提醒时保留原消息，后续直接点击原按钮。若客户端不支持保留某类页面／重复提交，由负责人准备可重复发送同一次提交的测试工具并给出操作方法；普通重新打开页面并发起新操作不能替代此项。
- 管理确认一般 60 秒有效。确认码从系统生成的真实按钮命令取得，不猜测。跨账号测试需要管理员事先准备能读取聊天按钮点击命令的工具，并把真实 `/tianjitown confirm ...` 命令交给另一账号。默认界面无法取得时记受阻，不能编一个码试错。取消、换人确认、修改小镇资料后的确认都应在有效期内完成，避免实际测成了超时。
