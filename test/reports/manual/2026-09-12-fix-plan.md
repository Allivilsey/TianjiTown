## 1. 放行 Residence 传送（报告 1）

定位：`ResidenceCommandGuard.onPlayerCommand/parse`。

目前把 `tp`、`teleport` 当作受保护命令，仅在目标同时满足活动小镇名称、受管理名称、系统领地等条件时放行；不满足条件甚至可能影响普通领地传送。

方案：识别 Residence 的传送子命令后直接退出本插件的拦截流程，不查询小镇状态，也不进入依赖异常时的拒绝分支。覆盖 `/res tp`、`/residence tp`、`teleport` 及可用的命名空间形式。传送是否合法由 Residence 自身处理；修改领地的命令仍走原有保护。

验收：镇内、镇外、成员、访客、普通领地、小镇领地及 Residence 查询异常场景均不由 TianjiTown 取消传送命令；领地写命令保护继续有效。

## 2. 小镇领地欢迎和离开消息（报告 2）

定位：`LandProtectionService`、`ResidenceLandProtectionService`、资料更新与领地修复流程。

当前创建和修复领地没有投影小镇的消息；Residence 继续使用默认模板。

方案：增加小镇展示名称的消息投影，内容为 `欢迎来到{town}`、`你已离开{town}`，使用小镇名称而非领地代码。通过 Residence 的 `setEnterMessage`、`setLeaveMessage` 写入本镇领地；本地 6.0.2.4 JAR 已确认具备这两个方法。创建、资料改名、启动同步、手动修复均同步更新，扩展区域复用所属小镇文案。沿用 `messages.yml` 文案管理。

验收：新建和已有小镇都显示正确中文名称，改名后立即更新，非本插件管理的领地不受影响。

实施说明：现有资料业务禁止修改镇名和代码，本次保留该规则，没有新增改名功能。资料保存同步当前名称，隔离测试使用名称变化的快照验证投影更新；启动、创建和修复同步实际数据库名称。

## 3. 初始成员拒绝后重选并重置邀请（报告 3）

定位：`TownApplicationUi`、`TownApplicationDrafts`、`TownInitialMemberDialogs`、`TownApplicationFormUi`、`TownApplicationStore`。

当前拒绝只修改成员确认状态；打开菜单仍渲染申请总览，提醒按钮只针对 `PENDING` 成员，因此无法重新邀请已经拒绝的人。

方案：拒绝后使本轮邀请失效，持久化“需要重选初始成员”的状态。申请人下次通过手册、服务台或旧申请链接打开时，保留名称、说明、规则等资料，直接进入初始成员选择步骤。保存新名单时重新生成整轮邀请，两人均需确认，并清除上一轮提醒冷却。已有选址仍有效时保留，过期时按现有选址规则重新选择。

邀请需要独立的轮次或令牌，回复必须同时匹配当前轮次和 `PENDING` 状态；不能只使用申请 ID、玩家 UUID，否则旧邀请可能确认新一轮。普通成员回复不应使另一名成员的同轮邀请失效。重选未提交时旧轮次同样不能继续修改确认结果。

验收：一人拒绝、两人拒绝、重新邀请同一人、换人、重启后重开菜单、旧邀请回调、重复回复及两人同时确认。

## 5. 静默同步成员 Residence 权限（报告 5）

方案：读取 Residence 实际 `padd` 权限组，使用逐项静默授权接口，保留权限组配置语义、逐项失败判断及 trusted 状态维护。仅消除成功授权输出，必要的失败日志继续保留。

验收：创建、入镇、退镇、修复均不输出授权列表；`isTrusted`、玩家权限集合及实际操作权限与修复前一致。

## 7. 管理员原因参数可选（报告 7）

定位：`TownCommandParser`、各管理员命令类、Lamp 参数注册、帮助及补全。

方案：所有真实的原因参数统一改为可选，省略或纯空白时使用 `管理员调整`；显式填写时保留完整多词原因。覆盖删镇、成员增删、镇长转移、投票取消、资金调整、税率调整等入口。业务层仍要求最终审计原因非空。

注意：`vote cancel` 的原因是独立必填参数，必须同步改为可选；仅修改解析器不足以修复。`member role` 目前借用 `reason` 字段解析角色，应拆分为必填角色参数，不能让默认原因误填角色。

验收：每个相关命令分别验证无原因、多词原因、缺少业务必填参数；审计默认值一致，角色、金额等仍严格校验。

## 8. 用管理员免费设置替换代购（报告 8）

定位：`TownAdminEconomyCommands`、`TownAdminCompletionEngine`、`BuffPurchaseStore` / 新设置业务、`BuffSettings`。

命令形式：`/tianjitown buff set <town> <buffkey> [time] [level]`。建议 `time` 沿用商店的整数周数，默认 1 周、1 级；1～4 周，等级 1～`min(5, maximum-level)`。测试服当前上限依次为 speed 5、health 5、diving 1、safe_fall 3、mining 3。

补全提供真实 Buff key、1～4 周及所选 Buff 合法等级，不再提示占位符。移除 `buff grant`，新增独立设置事务，直接覆盖该镇同 key 的效果，记录 `BUFF_SET` 审计并刷新成员。建议设置前后小镇余额完全相同，也不受商店营业开关限制；仍受管理员权限、运行时可用性、小镇状态及参数校验限制。

免费记录的 `price_minor` 为 0，后续被玩家重购时可退款额为 0。初始建表脚本当前要求 `price_minor > 0`，需改为允许非负值；付费购买在业务层保持正价校验。设置失败时恢复设置前状态，不走付费全额退款流程。

## 9. 重购 Buff 按剩余时间折算退款（报告 9）

定位：`BuffPricing`、`BuffPurchaseStore`、`BuffLifecycleStore`、`SelectedBuffQuote`、商店确认界面。

按旧记录实际支付金额及原有效期计算：

`退款最小货币单位 = floor(旧 price_minor × 剩余毫秒 / 原总毫秒)`

剩余时间限制为 0～原总时长；按旧订单折扣后的金额计算，不使用当前配置重新定价。管理员免费记录、已过期记录退款为 0。

同一事务内完成旧 Buff 失效、退款入账、新购买扣款、新 Buff 写入和审计。余额判断应允许使用此次退款，即 `原余额 + 退款 >= 新价格`。确认界面显示新价格、预计退款和预计净支出，提交时按同一时点重算，校验所确认的旧 Buff 身份，避免并发覆盖。退款以旧 Buff ID 形成唯一业务键，重复提交不重复退款。

实施说明：退款业务键包含旧、新两个 Buff ID，购买请求另有唯一幂等键。这样应用失败补偿并恢复旧订单后，新的合法重购仍可退款；只对旧 ID 设置永久唯一退款键会阻止这条路径。

特别处理现有 `refundActiveBuff`：它会全额退款后恢复最近的 `SUPERSEDED` 记录。引入剩余退款后不能原样保留，必须记录准确替换关系及本次折算额。若新效果应用失败且该订单仍为当前订单，补偿应撤销本次新扣款和旧退款，再恢复准确的旧记录；已被后续订单替换时不得回退后续订单或重复退款。数据库写失败则整体回滚。

验收：同级续购、升级、降级、折扣订单、到期边界、零元来源、余额仅在退款后足够、重复提交、并发购买及应用失败补偿。

## 12. 管理命令统一权限（报告 12）

定位：`plugin.yml`、`TownAdminPermissions`、`AdminAccess`、`TownAdminLamp`、补全及帮助过滤。

## 13. 删镇后彻底撤销 Buff（报告 13）

定位：`TownAdminApplicationCommands.deleteTown`、`TownDeletionStore`、`TownGovernanceActions`、`BuffRuntime`。

管理员删镇当前只完成数据库归档和 Residence 删除，没有刷新玩家；镇长解散的刷新又位于 Residence 删除成功之后。因此投影删除失败时也可能保留效果。数据库查询已限制活动小镇，但没有刷新就不会主动移除玩家现有效果。

方案：把归档后的 Buff 撤销做成管理员删除、镇长解散、重试共享的业务步骤。归档事务中终止该镇活动 Buff；归档提交后立即使已有刷新回调失效，并刷新归档前成员及待清理玩家，不以 Residence 删除成功为前提。利用已有归档成员快照处理重试，离线玩家在下次登录校准。

清理应扫描本插件 `buff_` 命名空间的所有实际 modifier，包括配置已移除或变更的属性，不能只按当前目录和内存索引删除。同步停用活动领地缓存。若玩家随后加入另一小镇，按其当前权益校准，不能延迟清除新镇效果。

验收：管理员删除、镇长解散、投影删除失败、离线成员、立刻重登、立即加入另一镇、过期异步回调及配置删项。

## 14. 首次创建 amu 成功后出现空指针（报告 14）

定位范围：`TownAdminApplicationDialogs.adminApprove`、`TownDialogService`、`TownProvisionRuntime`、`TownProvisioningStore.beginProvision`、`TownPersistence.findApplication`、`SitePolicy`。

现象以用户补充为准：首次申请 `amu` 后正常批准，出现创建成功提示后又报告空指针；后续重新申请并批准 `amu`、`AMU` 正常。撤回此前“由手动重复审批导致”的确定性归因，也不将名称大小写视为已确定原因。

已确认的代码缺陷：数据库准备建镇时释放选址预留，之后申请查询只读取未释放预留，因此 `application.territory()` 可能为空；`chargeAndBeginProvision` 在检查申请是否已经创建、是否处于失败重试之前就使用该值。该路径能够解释再次进入审批时的空指针，但目前还不能证明它就是首次正常审批后报错的完整触发链。

排查及修复方案：

1. 以首次 `amu` 的申请 ID 串联正常批准、数据库准备、预留释放、领地创建、结果回调及成功提示；对比后续两个正常申请。核对测试服部署 JAR 与当前源码的审批和 Dialog 实现，避免把源码中的现有保护误当作现场已验证行为。
2. 补充审批入口来源、操作者、Dialog 会话、操作 ID、申请状态/版本、关联小镇 ID、领地来源以及异常完整堆栈。追踪首次流程为什么在成功后再次进入，检查异步返回、旧页面回调与成功后的页面切换。当前源码已使用单次回调及会话消费，不能仅凭日志推定重复数据包、双击或自动重试。
3. 在领地检查和扣款前按最新申请与关联小镇状态分流：已创建且小镇活动时返回既有结果；创建中返回处理中；失败重试从关联小镇初始 `territory_units` 读取领地；小镇已归档时返回明确状态。首次审批才使用有效的选址预留。这样无论再次进入来自哪条回调，都不会解引用已释放预留或重复扣款。
4. 正常首次审批的后半段统一使用已创建小镇的领地快照，不重新依赖申请预留。结果通知与页面更新失败应单独记录，不能把已提交成功的建镇改报为业务创建失败。检查每次操作的完成回调只执行一次；实际发现的额外调用来源需修复，不能只屏蔽报错文本。
5. `SitePolicy` 等几何入口对缺失领地返回明确业务错误。该防护作为兜底，不能代替首次流程调用链的定位。

验收以正常首次创建为主：使用独立新库及未使用区域，正常提交并批准 `amu`，只操作一次批准，确认只创建一次、扣款一次、通知一次且无后续操作失败。重复多轮，并对照解散后重新申请 `amu`、`AMU`。再补充成功后的过期回调、异步回调延迟、两名管理员并发审批、失败重试和预留过期的回归测试。定位报告中应明确哪些路径已复现、哪些仅为防御性覆盖。
