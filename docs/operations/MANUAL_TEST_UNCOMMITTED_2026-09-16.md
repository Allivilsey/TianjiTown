## 通用操作指示

### 角色、命令与文件约定

下文的 `<管理员>`、`<申请人>`、`<成员甲>`、`<成员乙>`、`<访客>` 都要替换成真实在线玩家名；不要原样输入尖括号。测试镇示例代码为 `qatown`，必须换成当前用例实际代码。下列代码块中的命令逐行执行，不要整段当成一条命令发送。

- **管理员游戏内**：能操作 GUI，具备 `tianjitown.admin`；涉及 XConomy/CMI/PAPI 的管理命令还需对应权限。
- **普通玩家游戏内**：没有 OP 和 `tianjitown.admin`，但保留正常余额查询、付款权限。先用普通目标账户成功查询/付款，再测清算账户，避免把“本来就没有经济权限”当作隐藏成功。
- **服务器控制台**：示例命令省略开头 `/`。`stop` 后等服务器进程完全退出，再备份/改迁移样本。
- **文件管理器/文本编辑器**：所有 `plugins/...`、`logs/...` 都相对实际测试服根目录，不是本代码仓库目录。配置修改后保存 UTF-8；不要打开数据库当文本编辑。
- **数据检查工具**：打开停服后的独立数据库副本执行只读 SQL。若使用在线数据库查看工具，须明确使用只读连接，不执行下文未列出的修改语句。

开始前由管理员执行并保存输出：

```text
/version
/version XConomy
/version CMI
/version PlaceholderAPI
/tianjitown status
/xconomy help
/cmi balance ?
/cmi pay ?
/papi list
```

确认本服实际注册了 `xconomy:balance`、`xconomy:balancetop` 和 `xconomy:pay` 后再使用下文命名空间示例。若没有，按本服帮助/命令注册结果选择对应 XConomy 命令，记录实际命令；不要用 CMI 的同名别名代替 XConomy 验收。外部命令依据 [XConomy 作者命令及占位符说明](https://www.spigotmc.org/resources/xconomy.75669/)、[CMI 命令说明](https://www.zrips.net/cmi/commands/)、[PAPI 解析命令说明](https://wiki.placeholderapi.com/users/commands/) 核对；实际版本帮助优先。

### S1：进入菜单、提交申请和打开审核

1. 管理员执行 `/tianjitown handbook <申请人>`、`/tianjitown handbook <成员甲>`、`/tianjitown handbook <成员乙>`；三人右键收到的真正手册。也可由管理员执行 `/tianjitown open <玩家>` 打开目标玩家菜单。管理员为自己打开时同样填写自己的名字。
2. 申请人点“申请建立小镇”，依次填写基础资料、规则和两名**在线、无镇籍**的初始成员；示例名称“验收小镇”、代码 `qatown`、简介“人工验收用”、规则“测试期间勿交易”。在选择成员页先测“保存草稿并退出”，再从“继续小镇申请”返回并点“完成资料并发送邀请”。
3. 两名成员从“待办中心 → 建镇邀请”进入详情，按用例选择接受、拒绝或暂不处理。正常建镇要求两人都接受。
4. 申请人走到合法空地，打开“继续小镇申请 → 选择建镇地址”，完成预览/确认，再点“提交申请”。选址检查整个镇域，不只脚下区块；若冲突，按提示换位置，不能跳过校验。失败场景要求修改地形时，在提交之后、批准之前进行。
5. 管理员打开自己的主菜单，点“管理员审核 → 对应小镇”。正常申请点“批准”并完成确认。失败申请上的实际按钮是“重试批准”“解除锁定并要求修改”“取消申请并退款”“强制清理失败申请”；选择后完成确认页面。
6. “重试创建”“解锁修改”等为本文行为简称，以第 5 步的实际按钮名操作。管理员聊天命令 `/tianjitown application list` 用于核对队列，不能代替 GUI 批准操作。

### S2：每次经济/恢复操作前后的核对

管理员执行下列命令，操作前后各保存一次输出。升级前将清算名称替换为 `tax`；升级后使用 `tianjitown-tax`。

```text
/xconomy:balance <申请人>
/xconomy:balance tianjitown-tax
/tianjitown money view qatown
/tianjitown ledger view qatown
/tianjitown town view qatown
/tianjitown application list
/tianjitown audit 50
```

小镇尚未创建/已被回滚时，`money view` 或 `town view` 找不到对象可能正是预期，改用 S4 核对申请和费用。不要为了“让查询成功”新建同名镇覆盖证据。

捐款操作：**本镇成员**右键手册 →“公共资产”→“自定义金额捐款”，输入 `10.00` 并确认（测试玩家余额须足够）。以实际扣款为准核对玩家 `-10.00`、清算 `+10.00`、公共余额 `+10.00`，以及唯一捐款记录。若本服金额精度不接受该格式，使用同额的合法格式。

核对税款时每次只做一笔交易，记下商品/职业、付款者、收款者、成交总额、税率、补贴剩余额度；不要在多人持续交易期间比较聚合余额。玩家 GUI“公共资产 → 小镇账本”可翻页；管理员 `ledger view` 只显示最近项目，税款显示可能按日汇总，逐笔去 S4 查。

操作结束执行 `/tianjitown diagnose 7`。完整报告在 `plugins/TianjiTown/diagnostics`，控制台和异常详情在 `logs/latest.log`。报告中对账数据要和本次操作时间对应。

### S3：准备和切换数据副本

1. **U0**：旧 JAR、旧配置 `tax`、旧账户余额已核对的完整停服副本。保存世界、插件配置/数据库、账户数据和 JAR；故障测试每个分支都从独立副本开始。
2. **U1**：由 U0 完成 A01 后、尚未进行测试交易的完整停服副本。检查迁移文件 `state=COMPLETE`，UUID/余额与 U0 一致，配置是新名称。A02 正常交易另在 U1 的副本进行。
3. **F0**：按 E02 做出 `PROVISION_FAILED` 且费用已经托管的完整停服副本；保留失败地形。重试与三个恢复按钮分别复制 F0 测，不连续对同一份已处理申请测试所有按钮。
4. 每次恢复使用独立测试服目录/数据副本并核对连接目标，启动前确认不会连接生产经济数据。不要只还原 TianjiTown 数据而保留另一时间点的 XConomy、Residence 或世界数据。

### S4：SQLite 只读检查

TianjiTown 默认文件为 `plugins/TianjiTown/tianjitown.db`；先查看实际 `config.yml` 的 `database.file`。用 SQLite 查看器打开其停服副本，在 SQL 执行页逐段运行以下查询，并把 `qatown` 换成测试代码。UUID 在库内是 BLOB，以下显示为 32 位无连字符十六进制；对照迁移文件 UUID 时先去掉连字符。

```sql
-- 申请、费用、小镇绑定与最近失败原因
SELECT lower(hex(application_id)) AS application_id,
       lower(hex(applicant_uuid)) AS applicant_uuid,
       residence_name, status, application_fee_status, application_fee_minor,
       lower(hex(town_id)) AS town_id, last_error, version, updated_at
FROM town_applications
WHERE lower(residence_name) = 'qatown'
ORDER BY created_at DESC;

-- 最新申请关联的小镇与公共余额；不存在时先检查上面的申请绑定
SELECT lower(hex(t.town_id)) AS town_id, t.name, t.status, t.reuse_blocked,
       a.balance_minor, a.locked, a.lock_reason
FROM towns t LEFT JOIN town_accounts a ON a.town_id = t.town_id
WHERE t.town_id = (
    SELECT town_id FROM town_applications WHERE lower(residence_name) = 'qatown'
    ORDER BY created_at DESC LIMIT 1
);

-- 最近逐笔账本；避免只看按日合并后的聊天展示
SELECT entry_type, amount_minor, balance_after_minor, business_key, created_at
FROM ledger_entries
WHERE town_id = (
    SELECT town_id FROM town_applications WHERE lower(residence_name) = 'qatown'
    ORDER BY created_at DESC LIMIT 1
) ORDER BY created_at DESC LIMIT 50;

-- 最近审计：按本次申请 UUID、执行人和时间辨认
SELECT audit_id, actor_name, action, target_id, reason, detail, created_at
FROM audit_logs ORDER BY audit_id DESC LIMIT 50;

-- 初始成员确认状态；token 不需要复制到报告
SELECT lower(hex(m.application_id)) AS application_id,
       lower(hex(m.player_uuid)) AS member_uuid, m.confirmation_status
FROM application_initial_members m
JOIN town_applications a ON a.application_id = m.application_id
WHERE lower(a.residence_name) = 'qatown';
```

金额的 `_minor` 是最小货币单位，不可无条件当作元；按本服实际货币精度换算。清算账户真实 UUID/余额来自 XConomy，**不在** `town_accounts`。XConomy 的具体数据库文件和表名前缀先从自身配置/实际结构核实；迁移适配通过 XConomy API 读取 UUID、名称和余额；人工核对时对应账户列 `UID`、`player`、`balance`，隐藏列为 `hidden`。在其只读查看器中按名称 `tax`/`tianjitown-tax` 与迁移文件的 UUID 双重过滤核对，不猜表名，不用修改 SQL 修正测试结果。

### S5：信标观察站

1. 在镇 A 的已激活区选一块地，用完整金字塔放置信标并确保光束可见。测试镇长在信标界面放入支付材料、选效果、点击绿色确认按钮；只关闭界面不算提交设置。
2. 在同镇另一已激活区设置观察位置，水平距离源信标至少 100 格；这里是测试布局距离，不是对所有服务端配置下原版半径的假设。先关闭 TianjiTown 信标功能并等待已有效果消退，确认观察点没有原版来源覆盖，再开启功能。源旁始终留一人，区块停止测试除外。
3. 观察者打开物品栏查看效果名称、等级、剩余时间，录像覆盖至少两个刷新周期。测试失效时先录到一次续期，再改变来源，观察倒计时不再被抬高并最终消失；默认配置可先连续观察 30 秒，低 TPS 或状态更新尚未完成时延长并记实际 TPS。
4. 配置开关位置为 `plugins/TianjiTown/config.yml` 的 `territory.beacon.enabled`；切换后执行 `/tianjitown reload`。周期 `refresh-interval-ticks` 修改后完整重启。单独测试一种来源，避免另一座同效果信标掩盖失效结果。

  1. 使用四个独立测试目录分别构造本例四种配置；新装目录不用 U0 的生产数据，旧账户不存在分支先在 XConomy 确认名称和 UUID 均不存在。

## C. 实时信标扩散

所有续期判断都在原版信标作用范围外进行，避免把原版效果当作插件扩散。源区块须持续运行；观察失效时要计入信标自身状态更新、插件刷新和剩余药水时间。默认刷新周期为 100 tick（正常 TPS 约 5 秒），一至四层效果单次原版时长分别为 220/260/300/340 tick。以倒计时是否继续被刷新为主要证据，不要求拆除后瞬间消失。

  操作：每次恢复初始状态后，依次用不透明方块完全遮挡光束、破坏金字塔使其失效、拆掉信标；分别恢复光束、金字塔和信标。  
  预期：失效后远处效果不再续期并自然消退；即使金字塔仍完整，光束被阻断也不能扩散。恢复有效状态后重新续期，不必依赖旧数据库记录。

  3. 源旁玩家返回，确认区块恢复运算和效果恢复。若整镇都在模拟距离内，需在专用副本调整测试布局或模拟距离后重启，不能仅凭“走远了”算完成；缺少状态工具时该子项记阻塞。

  操作：远处观察者留在镇内，所有其他玩家离开信标附近，排除出生区块或其他保活来源；确认源区块停止方块运算/卸载。之后返回源区块。能区分区块等级的环境另测“已加载但不进行方块运算”。  
  预期：来源停止运行时暂停扩散，插件不主动加载或保活区块；恢复运算后重新验证并续期。无法确认区块状态时不得仅凭玩家距离判定通过。

## E. 建镇失败补偿与恢复

需要失败样本的用例优先使用确认过的失败副本。不得用“停止整个 Residence 插件”代替某个单次 API 失败并假定到达同一分支。若无法稳定得到所需状态，记录缺少的样本或注入点。

  1. 按 S1 完整完成申请、两名初始成员确认、选址、提交；批准前先用 S2 保存申请人/清算余额。
  2. 管理员进入审核详情点“批准”并确认，等待结果；申请人通过“小镇资料 → 小镇领地”进入传送/预览入口检查落脚点。
  3. 执行 S2/S4，检查 ACTIVE、费用已消费、唯一初始资金记录及两名成员；完整重启后重复检查。

  操作：全新提交并批准一份申请，完成建镇后使用默认传送入口；重启后核对小镇与成员。

  操作：申请完成选址后，在初始中心区块的 `(chunkX*16+8, chunkZ*16+8)` 柱上把最高方块置于世界高度上限附近，再批准。确认实际进入日志所示“默认传送点高度”失败；若提前被选址检查拒绝则本例未覆盖。另有样本时覆盖世界不可用、落脚空间不安全和设置传送点接口失败。  
  预期：已经创建的受控 Residence 被补偿删除，申请保持可处理的创建失败状态，未误报建镇成功；失败详情区分原失败和清理结果，申请费没有重复扣除。

## F. 任意申请强制取消与冷却

- [ ] **F01 · P0 · 取消已归档失败申请，不退款**

- [ ] **G01 · P1 · 旧 messages.yml 兼容**

  3. 普通玩家重新查询清算账户，检查新文本生效；结束恢复原文案并 reload，保留升级前自定义值未被覆盖的文件对照。

  操作：保留升级前自定义消息文件启动，触发邀请待办、已归档取消、账户不可查询提示；再修改一条已有自定义文案并执行 `/tianjitown reload`。  
  预期：新消息缺失时使用内置默认文案，不展示原始 key、未替换的 `{变量}` 或空白按钮；原有自定义内容保留，动态消息重载正常。

- [ ] **G02 · 专项 · CI 不应构建的事件**  

  **执行步骤：**

  1. 在含当前工作流的独立 Git 测试工作区/已存在远程测试分支操作，先确认远端接收了该 workflow；不要在当前未提交工作区混入 CI 测试提交。
  2. 分别提交并推送：仅文档、仅子模块 POM、根 POM 非顶层版本字段。逐次在 GitHub Actions 打开对应 push 的运行记录，保存触发事件与 job 状态。
  3. 对该分支创建/更新 PR，区分 PR 事件与同时发生的 push；无运行时还需核对 Actions 已启用，不能把整个仓库禁用 Actions 当通过。

  操作：在专用远程测试分支分别推送仅 Java/文档改动、仅子模块 POM 改动、根 `pom.xml` 非项目版本字段改动；另创建/更新 PR。  
  预期：不涉及根 POM 的 push 和单独 PR 事件不启动此工作流；根 POM 变更但项目顶层 `<version>` 不变时，`version` job 执行、`verify` 跳过，没有新的 TianjiTown 构件。若 PR 分支 push 同时修改根 POM，按 push 规则判断，不能认作 PR 触发。

- [ ] **G03 · 专项 · CI 版本变化与首次推送分支**  

  **执行步骤：**

  1. 在已有远程测试分支把根 pom.xml 的顶层项目 version 改成另一个合法测试版本，提交推送；不要仅修改依赖版本或子模块版本。
  2. Actions 中查看 version 输出 changed=true、verify 成功、可复现比较成功；下载 TianjiTown 构件，核对包含 JAR 和构建日志。
  3. 从指定测试基线新建另一个本地测试分支，在首次 push 中包含根 POM 变化，查看该次 version 输出 changed=false、verify 跳过；保存 before 为全零的事件证据。

  操作：已存在的测试分支修改根 POM 顶层项目版本并 push；另测新分支首次 push 且包含根 POM 变化。  
  预期：已有分支版本变化触发 `verify`，执行 Java 25 下的 `mvn -B -ntp clean verify`、两次构建产物字节比较，并上传 `TianjiTown` 构件。新分支首次 push 的 `before` 为全零时，即使版本有改动也跳过 `verify`；这是当前实现的预期，应在发布安排中计入。构件保存时长使用仓库/组织默认值，不再固定 7 天。
