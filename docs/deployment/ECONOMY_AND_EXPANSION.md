# 公共经济与领地扩张升级验收

> 当前 schema `7.0` 要求 QuickShop-Hikari 严格高于 `6.3.0.0`，税率固定为 5%～25% 且按 5% 调整，并为每笔税收提供同额服务器补贴。以下内容保留为旧版本发布记录。

本功能最初由 `1.2.0` 交付，数据库目标版本为 `3.0`。生产切换必须先完成本手册中的预发验证；代码完成不等于真实经济链路已经通过生产门禁。

## QuickShop 兼容决策

当前税务适配器要求 QuickShop-Hikari 版本严格高于 `6.3.0.0`，并使用新版增强税率事件与交易账户 API。插件启动时会核对版本和以下能力：税率事件、经济交易事件、成功购买事件、税款接收方切换以及 QUser 创建接口。版本或签名不匹配时不会注册动态税监听器，并在 `/townadmin status` 中给出警告；公共账本、查询和其他业务功能仍可用。

动态税只处理 QuickShop 交易：

- `SELLING` 商店的实际收款方是商店所有者。
- `BUYING` 商店的实际收款方是与商店交互的玩家。
- 实际收款方属于小镇时，使用该镇税率；否则税率为零。
- 税款接收方切换为 `phase3.settlement-account`，仅在 QuickShop 成功事件后写入小镇账本。
- 金额按 Vault 提供者的小数位转换为最小货币单位，税率按基点保存。

## 上线前准备

1. 停服备份 QuickShop H2、XConomy 数据库、`plugins/TianjiTown/tianjitown.db` 及其 `-wal`/`-shm` 文件，并记录清算账户的精确余额。
2. 在隔离预发服恢复上述备份，安装严格高于 `6.3.0.0` 的 QuickShop-Hikari 和当前 TianjiTown。
3. 确认 `phase3.settlement-account` 指向 XConomy 中专用且可由 Vault 以离线玩家 UUID 访问的账户，默认值为 `tax`；插件会采用 Paper 缓存中的实际名称大小写（例如 `Tax`），并在启动时复核建账结果。
4. 停止 QuickShop 原固定 5% 税和 DailyTaxEconomy 对该账户的独立写入，避免同一笔交易重复计税或产生无法归属的小镇外余额。切换期间只允许 TianjiTown 适配器为小镇成员交易设置税率。
5. 启动后执行 `/townadmin status`，确认数据库为 `7.0`、清算账户可用，并出现 QuickShop 新版 API 能力检查通过信息。

## 预发验收矩阵

每组交易都应同时核对玩家余额、商店库存、QuickShop 历史、清算账户余额、`/townadmin money view` 和 `/townadmin ledger view`。

| 场景 | 必须确认 |
|---|---|
| `SELLING` 商店 | 使用商店所有者所属小镇税率，税款进入清算账户和该镇账本 |
| `BUYING` 商店 | 使用交互玩家所属小镇税率，不使用商店所有者税率 |
| 普通玩家 | 不产生小镇税或小镇账本记录 |
| 在线/离线商店所有者 | 实际收款方识别一致，金额和税率一致 |
| 交易取消、库存不足、余额不足 | 不生成成功税收流水，不改变小镇分账 |
| 同一成功事件重复投递 | `quickshop_tax_records` 与账本各只有一条 |
| 数据库临时中断 | 交易恢复后执行历史核对和清算对账，不允许继续带差异消费 |
| 清算账户短款 | 自动锁定新的公共资金消费，账本查询、捐款与 `/townadmin money reconcile` 仍可用 |

QuickShop `6.2.0.10` 的成功事件没有可跨重启复用的稳定交易 ID。适配器可防止同一运行期事件对象重复入账，数据库也按业务 ID 幂等；数据库中断或进程崩溃后的最终完整性仍必须以 QuickShop 历史、清算账户和小镇总账三方对账为准。这是上线前必须实际通过的门禁。

## 公共资金验收

1. 成员通过 Dialog 分别捐赠整数和小数金额，确认 Vault 扣款与账本金额相同。
2. 模拟清算账户入账失败，确认玩家退款；若退款也失败，确认操作进入待补偿状态并停止后续消费。
3. 用 `/townadmin money adjust <小镇全名> <带符号金额> <原因>` 测试正负调账，确认原因、操作者、Vault 结果和账本流水完整。
4. 执行 `/townadmin money reconcile`，外部余额必须不小于所有小镇余额与待完成操作之和；短款被修复后再次对账应解除锁定。
5. 普通成员可从 Dialog 分页查看完整历史流水，原始账本记录不得被清理。

## 领地扩张验收

初始 Residence 是一个 3×3 区块单元。扩张只能占用原点周围固定 5×5 单元网格中的上下左右相邻单元，必须保持连通，最多 25 个单元。第 `n` 次扩张的价格为：

```text
ceil(base-cost + per-unit-increase × (n - 1))
```

验收以下情况：方向预览、四方向连续扩张、非相邻/越界拒绝、余额不足、区块冲突、两次并发确认、Residence 创建失败、重启恢复和管理员 `land reconcile ... repair`。数据库扣款与区块占位在同一事务中完成；Residence 投影失败必须退款并释放占位，重试不得重复扣款。

## 功能开关与回滚

```yaml
phase3:
  tax:
    enabled: false
  consumption:
    enabled: false
```

修改后执行 `/townadmin reload`。`tax.enabled: false` 立即停止新的动态小镇税，`consumption.enabled: false` 立即停止捐款和扩张；既有账本查询、退款、恢复和清算对账不受影响。

如需回滚，先关闭两个开关并完成三方对账，再停服备份。`3.0` 数据库包含旧版本不了解的新表和多区域领地结构，不能直接将 `1.1.0` JAR 指向已迁移数据库；必须同时恢复升级前的 SQLite、QuickShop、XConomy 数据和 Residence 投影备份。任何已在 `1.2.0` 期间发生的资金或扩张变动，都应先生成审计清单并人工决定如何带回旧环境。
