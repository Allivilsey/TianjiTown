# 公共经济与领地激活部署验收

适用于 `1.0.0`。当前 QuickShop、Jobs、GlobalMarketPlus 共用小镇税率和补贴额度；已发布 schema `1.0` 的生产数据库通过 `V1_1` 新增申请费与收入税操作表，升级步骤见 [SQLite 手册](../operations/SQLITE_AND_BACKUP.md)。

## 经济接入

| 收入来源 | 税务归属 |
|---|---|
| QuickShop SELLING | 收款的商店所有者所属小镇 |
| QuickShop BUYING | 与商店交互、实际收款的玩家所属小镇 |
| Jobs | 获得工资的玩家所属小镇 |
| GlobalMarketPlus | 获得成交收入的玩家所属小镇 |

非成员收入不收小镇税，其他未接入 Vault 转账不征税。初始税率 5%，可设为 5%～25% 的整数百分比。税额按 Vault provider 的货币精度处理。

QuickShop-Hikari 税务接入要求至少 `6.3.0.0` 且事件、税款接收方和交易账户 API 能力通过。接口不匹配会报告并停用对应动态税务接入；检查 `status` 和日志，不要只看依赖已安装。QuickShop 税款接收方切换到专用清算账户，成功交易后写小镇分账。

## 部署准备

1. 按 [备份手册](../operations/SQLITE_AND_BACKUP.md) 在同一停服时间点备份 TianjiTown、Residence、QuickShop、XConomy，记录清算余额，在隔离服验证。
2. `economy.settlement-account` 默认 `tianjitown-tax`；已有配置为 `tax` 时启动自动更名，保留旧账户 UUID 和余额。确保清算账户专用，没有其他插件擅自清理或分配其资金；不要在升级前手工将该配置改为新名称，否则插件不能据旧配置确认 `tax` 的归属。
3. 检查 QuickShop 固定税或其他经济插件的独立税收规则，避免同笔交易重复征税或混入无法归属的清算金额。
4. 启动后执行 `status`、`diagnose 7`，核对接口状态、外部余额、内部余额和诊断报告。

## 清算账户隐藏

- 当前 Vault Economy provider 必须是 XConomy。启动时通过 XConomy 的持久 `hidden=1` 标记隐藏实际清算账户，立即刷新 `/baltop`、全服总余额和 `%xconomy_top_*%`、`%xconomy_sum_balance*%` 共用的缓存；每分钟检查并恢复隐藏状态。
- 安装 CMI 时，插件通过 CMI 接口将该账户的精确名称追加到 `Economy.BalTop.Exclude`，保存配置并刷新 CMI 自己的排行榜。已有排除项保留。CMI 是可选依赖。
- 过滤发送到客户端的账户名称、UUID 补全建议。普通玩家不能通过 `balance`、`bal`、`money`、`pay` 等经济命令或 `/cmi` 对应子命令直接查询/操作此账户；包含命名空间的命令也受保护。`tianjitown.admin` 管理员与控制台保留明确输入账户后的对账能力。
- 隐藏不修改账户余额、UUID、玩家余额或小镇账本，也不把既有账户转换为 XConomy 非玩家账户。不要为了隐藏切换 `non-player-account` 的账户识别规则。
- 首次隐藏失败会阻止小镇运行时启动并报告原因；运行期复查失败单独记录日志，不妨碍原有资金对账任务。XConomy/CMI 升级后应重新验收接口能力。
- 覆盖范围是 XConomy 的排行/总额、CMI 的经济排行及已识别的玩家命令入口。其他插件若自行遍历 Vault 账户、直接读取数据库或用任意占位符查询指定账户，仍需在对应插件配置中排除；Vault 没有统一的全局隐藏接口。管理员诊断和审计日志保留真实账户信息。

验收：准备有余额的清算账户和普通玩家账户，分别检查 XConomy/CMI 排名、XConomy 总额与 PAPI 变量；重启后重复检查，确认清算余额保持一致。再验证普通玩家的直接余额查询、命令补全，以及管理员对账、捐款和三种税源结算。

## 生产服旧账户自动改名

升级前保持原有 `economy.settlement-account: tax` 配置，按备份手册停服备份后替换 JAR 并启动。使用 XConomy `UUID-mode: Default`，首次迁移时不能有在线玩家。其他 UUID 模式会明确拒绝自动改名，不能为了迁移随意改变生产服的 UUID 模式。

自动流程在小镇运行时及三种税源注册之前执行：

1. 按原配置查找账户，同时核对 Paper 与 XConomy UUID。真实玩家账户、重名、目标名称/UUID 已被占用（即使余额为零）和数据库读取失败均中止迁移。
2. 将原名称、UUID、原余额及 `PREPARED` 状态落盘到 `plugins/TianjiTown/settlement-account-migration.properties`，再调用 XConomy 原生名称更新流程。只更改原记录的名称，不扣款、不存款、不创建新账户，因此不会引入 XConomy 的新账户初始余额。
3. 复核名称、UUID 和余额；备份原配置为 `config.before-settlement-account-migration.yml`，原子保存新配置，再把记录标为 `COMPLETE`。之后 Vault 和 QuickShop 使用记录中的原 UUID，新名称为 `tianjitown-tax`。迁移后的账户仍应用排行/总额隐藏，CMI 和普通玩家查询也屏蔽旧名称。
4. 若在改名后、保存配置前中断，下次启动通过已记录的 UUID 查明改名结果并继续，不重复转账。无法确认身份或发现迁移期间余额变化时锁定小镇写入并报告原因；不擅自回滚账户或调整余额。

`settlement-account-migration.properties` 同时是长期账户身份绑定文件，完成后也不能删除；备份、迁服和恢复时必须与 TianjiTown、XConomy 数据一同保留。迁移完成后的正常收支不会被恢复为迁移前余额。旧 `tax` 是同一个 UUID 的旧名称，不会留下第二个有余额的账户。

插件同时拒绝使用清算账户 UUID 登录游戏，防止离线身份被玩家占用后将系统账户改回玩家名称。

只迁移当前配置确实指定的 `tax`（兼容实际名称大小写）。自定义账户、已经配置新名称但没有迁移记录的环境，不会扫描并接管其他插件的 `tax`。原配置为 `tax` 但确认账户不存在时，只更新配置，后续按新安装流程创建新账户。

生产验收：核对日志中的 UUID 与升级前一致、余额未变、只存在一个清算账户，再执行 `diagnose 7`，测试捐款和三种税源，并重启复查绑定、排行和总额。实现已对 XConomy Paper 2.26.3 的原生名称更新与隐藏接口做隔离数据库验证；仍应按服务器自身依赖组合进行上线验收。

## 税收与补贴验收

每组交易核对玩家余额、交易结果、外部插件记录、清算余额、小镇余额及账本。

Jobs 5.2.6.6 工资税在工资实际 `depositPlayer` 返回成功之后收取。适配器仅包装 Jobs 自己的付款委托，保留付款缓冲，不替换全局 Vault provider；取消工资、付款失败、服务器税账户入账不触发小镇税。停用小镇插件时撤销自己的观察器，Jobs 重载后重新核验接口；升级 Jobs 必须重新验收付款链路。

GMP 1.4.1.4 的 `Transaction-After-Taxes: false` 表示成交时缴税，`true` 表示上架时缴税。小镇税基为 GMP 税后收入：普通出售记录交易前参数，零售核验实际累计税增量，批发按原生 Vault 税额公式并核验参数未变化；GMP 对 Vault 没有最低 1 元税，不额外加此下限。上架已缴税按售出数量/原上架数量分摊历史税额；拍卖合并已缴税与最终补税或退款。缺少可靠税额快照或交易期间关键参数变化时报告 `INCOMPLETE`，不收估算税。

GMP 成交是否成功仍以 GMP 原生成功事件为准：它可能忽略经济提供者的付款失败，也可能为离线卖家延迟发款。本插件没有修改 GMP JAR，也不声称该事件能证明玩家已经到账；上线验收需要核对 `Change-Balance-Only-When-Online` 和对应离线流程。此限制不影响小镇自身收税操作的持久化及异常恢复。

- 分别验证 QuickShop 出售/收购、在线/离线店主、Jobs 工资、GlobalMarketPlus 成交和非成员交易。
- 失败、取消、库存不足和余额不足的交易不能生成成功税款；重复事件不能重复入账。
- 三种收入共用每镇每周 `10000.00`、每 12 小时 `2000.00` 补贴上限。单笔提供等额补贴，额度不足时部分补贴，耗尽后仍入税款。
- 固定上海时间周一 04:00 和每日 04:00/16:00 切换补贴窗口；重试沿用首次预留周期。
- 账本按每日 04:00 分日，Jobs 显示职业收入，QuickShop/GlobalMarketPlus 显示商店收入；税款和实际补贴正确汇总，底层明细保留。

QuickShop 诊断只核对本地已记录税款对应的历史，不能发现全部外部漏记，也不能证明历史收款账户。查询异常或达到 1000 条扫描上限标记 `INCOMPLETE`。Jobs 与 GlobalMarketPlus 不属于这项 QuickShop 历史逐笔核对，需另查对应收入记录。

## 公共资金和补偿

领地激活、Buff 购买及其退款只调整小镇内部账户，不直接改变 Vault 清算账户余额。清算对账计入全部小镇内部余额、尚未关联小镇的确定托管申请费、`EXTERNAL_APPLIED` 操作金额，并抵减已被对应小镇账户锁隔离的负向 `COMPENSATION_REQUIRED` 操作。退款执行中或结果未知的独立申请费暂不计为可用资金，必须先核账。外部余额不得低于上述合计（最低为零），允许富余。验证短款锁时，应先核对当前外部余额和最低应有余额，再从隔离环境的外部账户扣除富余金额及测试缺口，不能假定购买后两边仍相等。

- 测试整数、小数捐款，个人扣款、清算入账与内部账本应一致。
- 清算入账失败应退款；退款失败在当前运行期最多重试 8 次，按 1、2、4、8、16、30、30、30 秒退避。成功后还要清算复核；超过上限或中途停服转人工核对，不重复补账。
- `money adjust` 正负调账同时改变清算余额和内部余额，记录原因及操作者；它不能仅修正外部短款。
- 清算短款锁定新的公共消费；捐款和查询仍可用，但若管理员关闭消费总开关，捐款也暂停。补正后等待后台清算对账，再检查账户锁定状态。
- 成员可分页查看完整历史，管理员 `ledger view` 仅展示最新 45 个项目。

## 领地激活

审批通过后，小镇立即获得以初始区域为中心的 5×5 单元网格，共 25 个区域（每区域 5×5 区块，合计 400×400 方块）。初始区域自动激活并拥有完整小镇 flag；其余 24 个区域仅禁止创建、追加、调整或设立子领地，其他行为与野外一致。激活区域必须与已激活区域保持四方向连通。首块默认 `5000.00`，第 n 次价格为 `5000 × 1.05^(n-1)`，每块向上舍入后求和；详见 [定价](PRICING.md)。

验证单格和批量选择、报价变化、非相邻/越界拒绝、WorldBorder 缓冲、余额不足、区块冲突、并发确认、Residence 失败退款及重启恢复。数据库内扣款与占位同事务，投影失败需释放占位和退款。

批量恢复失败时逐一核验并清理整批受控区域，包括停服前已创建和本次尚未遍历的区域；世界、边界或系统所有权不符时停止清理并保留待恢复记录，不先退款。最终数据库提交结果未知时保留外部投影，等待恢复确认，避免把已提交的领地拆除。

未激活区域由小镇预留索引阻止圈地，不创建带有默认 flag 的 Residence；重启从数据库中的小镇初始区域恢复预留范围。数据库 territory_units 记录已激活区域，全部归属范围由初始区域确定。激活成功后才加入 Residence area，失败退款并撤回新保护，预留归属不受影响。删除小镇时释放预留。

Residence 每个 area 水平为 80×80 方块，最大坐标为最小坐标 +79。不能只凭 Residence 局部可视化判断区域缺失；结合小镇领地预览、`land reconcile`、area 列表和实际权限测试。激活预览和购买通过镇长地图完成。

## 暂停与恢复

把 `economy.tax.enabled`、`economy.consumption.enabled` 设为 `false` 后执行 `reload`，分别停止新税收与捐款/激活等新消费入口；已提交退款、恢复和查询仍可进行。维护模式本身不停止税务和后台任务。涉及回退时停服保留当前副本，使用已验证的整套备份恢复，不将旧 JAR 直接指向未知结构数据库。
