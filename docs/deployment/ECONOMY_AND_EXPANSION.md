# 公共经济与领地激活部署验收

适用于当前 `1.0.0` 构建，数据库 schema `1.1`。小镇公共资金以 `town_accounts` 和 `ledger_entries` 为准；Vault 仅处理玩家钱包。插件不再创建、改名、隐藏或对账 XConomy 清算账户。

## 经济接入

| 收入来源 | 税务归属与处理 |
|---|---|
| QuickShop SELLING | 商店所有者所属小镇；QuickShop 发放税后收入，交易成功后小镇记税款 |
| QuickShop BUYING | 与商店交互、实际收款的玩家所属小镇；同上 |
| Jobs | 工资实际存入玩家钱包成功后，扣玩家税款并记小镇账本 |
| GlobalMarketPlus | 按可靠成交收入计算并扣玩家税款，再记小镇账本 |

非成员收入不收小镇税，其他未接入 Vault 转账不征税。初始税率 5%，允许 5%～25% 的整数百分比，沿用 Vault provider 的货币精度。

QuickShop-Hikari 要求至少 `6.3.0.0` 并通过事件/API 能力检查。本项目核查过 `6.3.0.1` 的配置及字节码：税后收入与税款接收方独立，`taxer(null)` 跳过税款存入账户。适配器仅对匹配的小镇交易清空税款接收方，继续使用 QuickShop 原生扣税和成功事件；不修改 QuickShop 全局配置，也不在成功后再次扣玩家钱。例：成交 100，税率 5%，买家扣 100、卖家得 95、小镇税款入账 5（如有补贴另记）。

QuickShop 的 `shop-tax.account: ""` 可全局关闭税款存入账户，但小镇适配不依赖该配置。若希望彻底退役旧 tax 账户，应检查其他插件及非小镇交易是否仍使用它，再由运维清理；插件不会清空其历史余额。

## 从托管账户版本升级

1. 正常停服，保存同一时间点的 TianjiTown、Residence、QuickShop、玩家经济数据和配置/JAR。共享玩家经济数据库时，暂停其他服务器写入以获得一致备份。在隔离服先验证恢复。
2. 替换 JAR，沿用原小镇数据库。Flyway `V1_1` 新增申请费与收入税操作表，同时保留各镇余额、流水、申请费和经济操作记录，只移除旧 `SETTLEMENT_RECONCILIATION` 锁；若仍有待核实资金操作，转换为该镇操作锁。其他原因的锁保留。
3. 不导入、不分配旧 tax / tianjitown-tax 余额，也不需要账户改名。旧 `economy.settlement-account`、`economy.reconciliation-interval-minutes` 配置不再生效。旧 `settlement-account-migration.properties` 不再参与启动，备份中可保留供回退使用。
4. 执行 `status`、`diagnose 7` 和 `money pending`、`money tax pending`、`money subsidy pending`，核对余额及遗留操作。结果未知的旧付款不自动重放；通过现有恢复命令核实。已确认待退的申请费直接退入玩家钱包。
5. 验收捐款、申请费退款、三种税源、补贴、消费及调账后再开放。新版本不再维护旧账户的隐藏、命令屏蔽或登录保护；清理旧账户前应先解除它在其他系统中的引用。

## 税收与补贴验收

税款、小镇余额、补贴额度和账本在同一个 SQLite 事务内更新。三种收入共享每镇每周 `10000.00`、每 12 小时 `2000.00` 补贴上限；单笔等额补贴，额度不足时部分补贴，耗尽后仍入税款。补贴不调用 Vault。

固定上海时间周一 04:00 和每日 04:00/16:00 切换补贴窗口，同一运行期重试保留首次记账请求时间；旧的已持久化补贴预留沿用原周期。账本按每日 04:00 分日。

- 核对 QuickShop 出售/收购、在线/离线店主、Jobs、GMP 和非成员交易。失败或取消不能增加小镇税款；重复回调不能重复入账。
- 核对玩家、各镇余额和税款/补贴流水；无需外部清算余额。
- 注入账本写入失败后，税款、补贴、额度全部回滚；重试不得再次扣玩家钱。
- 核对跨税源共享额度、部分补贴、耗尽以及时间窗口切换。

Jobs 5.2.6.6 仅包装自身付款委托，在工资 `depositPlayer` 成功后触发税款收取，保留工资缓冲；取消工资、付款失败、服务器税账户入账不触发小镇税。停用时撤销观察器，升级后需重新验收。

GMP 1.4.1.4 按 `Transaction-After-Taxes` 及交易类型核实税后收入，缺少可靠税额快照时报告 `INCOMPLETE`，不估算扣税。GMP 成功事件可能不能证明玩家实际到账，离线延迟发款仍需按 `Change-Balance-Only-When-Online` 配置验收。

QuickShop 历史诊断仅检查本地已记录税款对应的交易，不能证明全部外部交易均未漏记；查询异常或超过 1000 条扫描上限标记 `INCOMPLETE`。Jobs/GMP 另查收入记录。

## 公共资金和异常恢复

捐款及申请费仅扣玩家钱包；退费仅给玩家入账。领地激活、Buff 消费/退款、系统补贴和管理员调账全部在小镇数据库内完成。`money adjust` 同事务写余额、流水和审计，不改变任何 Vault 账户。

数据库重试只重试记账，不重复外部扣款。已知扣款成功但账本写入失败会重试入账；付款结果未知时保留操作供管理员核实，不盲目退款或重新扣款。极端停服窗口可能需要人工补账，不提供跨插件强一致事务。QuickShop 成功事件到首次 SQLite 提交之间的内存记录可能因崩溃丢失，可凭外部交易历史和管理员调账处理。

核实或完成旧退款后，直接解除相应资金操作锁，不等待外部账户对账；账本不一致和其他未决操作仍保留保护。不再因全服税收账户短款冻结各镇。

## 领地激活

审批通过后，小镇立即获得以初始区域为中心的 5×5 单元网格，共 25 个区域（每区域 5×5 区块，合计 400×400 方块）。初始区域自动激活并拥有完整小镇 flag；其余 24 个区域仅禁止创建、追加、调整或设立子领地，其他行为与野外一致。激活区域必须与已激活区域保持四方向连通。首块默认 `5000.00`，第 n 次价格为 `5000 × 1.05^(n-1)`，每块向上舍入后求和；详见 [定价](PRICING.md)。

验证单格和批量选择、报价变化、非相邻/越界拒绝、WorldBorder 缓冲、余额不足、区块冲突、并发确认、Residence 失败退款及重启恢复。数据库内扣款与占位同事务，投影失败需释放占位和退款。

批量恢复失败时逐一核验并清理整批受控区域，包括停服前已创建和本次尚未遍历的区域；世界、边界或系统所有权不符时停止清理并保留待恢复记录，不先退款。最终数据库提交结果未知时保留外部投影，等待恢复确认，避免把已提交的领地拆除。

未激活区域由小镇预留索引阻止圈地，不创建带有默认 flag 的 Residence；重启从数据库中的小镇初始区域恢复预留范围。数据库 territory_units 记录已激活区域，全部归属范围由初始区域确定。激活成功后才加入 Residence area，失败退款并撤回新保护，预留归属不受影响。删除小镇时释放预留。

Residence 每个 area 水平为 80×80 方块，最大坐标为最小坐标 +79。不能只凭 Residence 局部可视化判断区域缺失；结合小镇领地预览、`land reconcile`、area 列表和实际权限测试。激活预览和购买通过镇长地图完成。

## 暂停与恢复

把 `economy.tax.enabled`、`economy.consumption.enabled` 设为 `false` 后执行 `reload`，分别停止新税收与捐款/激活等新消费入口；已提交退款、恢复和查询仍可进行。维护模式本身不停止税务和后台任务。涉及回退时停服保留当前副本，使用已验证的整套备份恢复，不将旧 JAR 直接指向未知结构数据库。
