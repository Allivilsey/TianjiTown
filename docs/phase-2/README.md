# 第 2 阶段发布与验收

版本：`1.1.0`

## 发布前

1. 使用 JDK 25 和 Maven 3.9+ 执行 `mvn -B clean verify`，确认生成 `tianjitown-paper/target/TianjiTown-1.1.0.jar`。
2. 停止旧版写入口，并按 `docs/phase-0/SQLITE_AND_BACKUP.md` 备份 TianjiTown SQLite、Residence 与相关依赖数据。
3. 在数据库副本上启动 `1.1.0`，确认 Flyway 从 `1.1` 升级到 `2.1`，已有小镇、申请、成员和领地均可读取。
4. 检查并合并 `config.yml` 的 `phase2.governance` 与 `phase2.voting` 配置。旧配置缺少这些键时会使用代码中的安全默认值。

## 升级步骤

1. 停止 Paper，保留旧 `1.0.0` JAR、配置和完整备份。
2. 替换为 `TianjiTown-1.1.0.jar` 后启动服务器。
3. 执行 `/townadmin status`，确认门禁为 `READY`、schema 为 `2.1`。
4. 对所有现有小镇执行 `/townadmin land reconcile all`，确认成员 UUID 与 Residence 权限一致；需要修复时再显式执行 `repair`。

## 验收重点

- 镇长可在成员列表将普通成员任命为 `OFFICER`，官员可审核入镇申请；降职后权限立即失效。
- 镇长移除普通成员或官员后，数据库成员关系和 Residence 玩家 flags 同步清理，镇长不能通过普通移除流程被删除。
- 镇长转让只有候选成员明确接受后生效；拒绝、过期、重复点击和重启不会产生两个镇长或无主 `ACTIVE` 小镇。
- 修改规则会递增规则版本；成员下次登录收到提醒，打开主菜单时必须确认最新版本。
- 投票创建时冻结符合活跃窗口与最低入镇时间的选民，目标成员不计入选民；每个 UUID 只能投一次。
- 同一小镇任何时刻只能存在一条开放投票；同类型、跨类型和并发创建均应安全拒绝。
- 踢人赞成票必须严格超过 50%，强制换镇长达到 2/3；到期和全员投完均只结算一次。
- 归档前成员角色与加入时间写入 `town_archived_members`，审计日志和小镇资料继续保留。

## 回滚

Flyway `2.0` 会增加治理表并替换成员角色约束，`2.1` 会收紧同镇开放投票约束；不能让 `1.0.0` 直接写入升级后的生产数据库。需要回滚时：

1. 停止服务器并保存升级后数据库副本用于审计。
2. 恢复升级前 SQLite 与 Residence 备份。
3. 恢复 `1.0.0` JAR 和旧配置后启动。
4. 执行 `/townadmin status` 与领地只读对账，确认旧版数据链路恢复后再开放玩家入口。
